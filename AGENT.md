# mqtt-kafka-bridge guidance

Current scope includes message definitions, configuration, the generated MQTT-to-Kafka mapper and the user-authored telemetry processor whose QoS/topic wiring and correctness fixes were explicitly requested. Keep the existing bootstrap, standard Kafka infrastructure configuration and WebFlux/Actuator foundation. The user explicitly authorized completing MqttClientConfig: construct a disconnected HiveMQ MQTT 5 async client bean using bridge.mqtt.identifier, bridge.mqtt.host and bridge.mqtt.port. The user also authorized moving connectSubscriber into MqttClientConfig; keep it explicit, asynchronous and error-preserving. The telemetry processor injects its dependencies and performs no broker operations during bean creation. The user later authorized the startup chain: MqttClientConfig registers an ApplicationRunner only under the deployed profile, connecting before subscribing asynchronously. Compose selects deployed; default/local startup stays offline. Keep the three-second bounded MQTT disconnect cleanup outside request/event paths. The user authorized fixing the existing subscription/forwarding code: use the configured Mqtt5Subscribe request, explicit subscribe() after connection, JSON byte serialization, deviceId keys, constructor-injected mapper/Kafka destination and asynchronous error logging. Do not add further startup hooks, new routing, Cloud functions, retries, watering/device logic or additional processing without a later explicit request. HiveMQ MQTT Client replaces Paho; do not reintroduce Paho or its Spring Integration adapter. Preserve the MQTT 5 client selected in the user’s configuration class.

The intended bridge transports one complete MQTT observation into one complete raw Kafka record, keyed by deviceId. Separate downstream Device Processor and Telemetry Processor applications consume the raw topic using distinct groups. Keep envelope, battery/errors and sensor payload together in the message definitions. Soil is resolved downstream from sensorId. A device can report multiple sensors in different soils; never require soilId or assume one sensor/soil per device. No database, calibration, notifications, watering decisions or pump logic belongs here.

Exactly two authoritative OpenAPI documents under src/main/resources/openapi/ define MQTT input and Kafka raw output: mqtt-inbound.yml and kafka-raw-telemetry.yml. Shared payload/error schemas belong to inbound and are referenced by outbound. Preserve the supplied MQTT example and full outbound example. Generate message DTOs during Maven generate-sources and the explicitly authorized MapStruct mapper during compilation. The mapper converts one MqttTelemetryMessage to one complete KafkaRawTelemetry, preserving all fields, diagnostics and extensible sensor measurements. Keep strict source/target field checks and tests for different sensors. Generate no APIs/controllers or broker processing code. Never edit generated files under ignored target/.

Use Java 25 without preview, compatible stable Spring Boot, WebFlux/Reactor, Spring Kafka, Spring Cloud Stream/Function, HiveMQ MQTT Client, Maven Wrapper, JUnit Jupiter, Reactor Test and Testcontainers in one module. Lombok and SLF4J remain explicitly authorized, with Boot-managed versions and explicit Lombok annotation processing. No Spring MVC, Reactor Kafka, databases or Kubernetes. Pin unmanaged dependencies/plugins/images and verify compatibility using official documentation.

Follow TDD and KISS for meaningful changes: write/run a failing test, confirm its expected failure, then implement the smallest passing change. Report actual executions only. Avoid speculative layers or empty services. Use constructor injection and immutable typed properties. Update relevant tests/documentation. Preserve unrelated edits and the staged index.

Run ./mvnw verify for the real Kafka connectivity test and HiveMQ/Mosquitto-to-Kafka integration test; Docker is required and must not silently skip. Use ./mvnw clean verify after deleting generated contracts/classes. Keep publishers, orchestration and bounded broker waits in tests. Await SUBACK before publishing, assert configured topic/QoS and key/payload, and disconnect test clients. Never claim connectivity from unit tests alone.

Keep standard Kafka settings under spring.kafka.* and MQTT/topic settings under bridge.*. Do not restore obsolete Cloud function definitions or bindings; function autodetection stays disabled while the existing Stream dependency remains installed. The processor receives its Kafka destination from bridge.topics.telemetry. No startup broker connections outside the deployed profile and no automatic topic provisioning. Only health/info are exposed by default. Keep test config isolated from developer settings.
